## Why

Today the dashboard shows Revenue, Kitchen Speed, Staff Performance and a "forecast" that are hardcoded fallback numbers — the app has no POS, no ticket-time source, no staffing data. Only the `reviews` table has real signal. The plan strips the fiction and shows only what we can actually measure from that table, with honest "Not connected" states for the rest.

## What we actually have

`reviews` columns we can trust: `restaurant_id`, `rating_food`, `rating_service`, `rating_ambience`, `tags[]`, `comment`, `reward_code`, `reward_redeemed`, `created_at`.

Everything on the dashboard has to derive from these.

## New Executive Brief layout

Real, computed metrics (4 cards):

1. **Guest Satisfaction** — avg of `(food+service+ambience)/3` over last 7 days · delta vs previous 7 days.
2. **Reviews this week** — count last 7d · delta vs prior 7d.
3. **Reward Redemption** — `reward_redeemed = true` / total, last 30d · delta vs prior 30d.
4. **Top Complaint Theme** — most frequent tag among reviews rated ≤3 in last 14d (e.g. "slow service"), with count. If none, show "No recurring complaints".

Each card shows: value, delta arrow, and a small "based on N reviews" caption so the sample size is visible. If N=0 → render an "Awaiting reviews" state instead of a number.

Sub-scores strip (below the 4 cards): Food / Service / Ambience 7-day averages as thin bars — pure DB aggregates.

**Remove** the Forecast card and the Risk Alerts card in their current mock form. Replace with:

- **Review Signals** panel — real, generated by the existing `reviews-intel` server fn from actual review rows (praise / complaints / themes / urgent issues). Already implemented, just surface it here instead of only on `/reviews`.
- **AI Action Queue** — keep, but re-scope: prompt now only sees the real aggregates + review clusters above, and is instructed to produce actions grounded ONLY in review data (e.g. "Reply to 3 unaddressed 2-star reviews", "Investigate 'cold food' — 4 mentions this week"). No inventory/staffing/revenue actions. Each action shows the source review IDs it's based on.

**Not-connected rail** (small, honest footer strip): three greyed tiles — "Revenue · Connect POS", "Kitchen Speed · Connect KDS", "Staff Performance · Connect roster" — each with a "Coming soon" chip. Makes it obvious what's real vs pending, without pretending.

## Code changes

- **`src/lib/brief.functions.ts`** — rewrite:
  - Add a new server fn `getRestaurantMetrics` that loads reviews for the caller's restaurant via `requireSupabaseAuth` and computes the four metrics + sub-scores + top complaint tag in SQL/JS. Pure data, no AI.
  - Rewrite `generateDailyBrief` to accept `{ metrics, reviewClusters }` and only produce (a) greeting + headline and (b) the grounded action queue. Drop `forecast`, drop `metrics` from AI output (metrics come from DB), drop generic mock risks. Delete the current `fallbackBrief` mock numbers.
  - If `LOVABLE_API_KEY` missing or AI fails: still render, with a neutral headline and empty action list — never fake numbers.

- **`src/routes/_authenticated/dashboard.tsx`** — rewrite the page:
  - Fetch metrics first (fast, deterministic), render cards immediately.
  - Then fetch review clusters + action queue in parallel and stream in.
  - Empty-state variants for zero reviews on the whole page.
  - New "Not connected" rail component at the bottom.

- No schema changes. No new tables. No new secrets.

## Out of scope

Building a mock POS, manual daily-numbers entry form, or any inventory/staff modules. Those come later behind their own "Connect" flow.
